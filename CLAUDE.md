# Project Instructions

  приводят к принципиально разной реализации.
- Решения, которые принял сам (допущения, компромиссы, отложенный объем),
  проговариваешь в ответе.

- Отвечай на русском, коротко и по делу.
- Общаемся на ты, без фамильярности.
- Вопросы и развилки задавай интерактивным выбором вариантов, а не текстом:

  фазе планирования (`/opsx:explore`, `/opsx:propose`, `/opsx:update`).

## Границы репозитория

Фронт живет отдельным репозиторием - `../messenger`. Этот репозиторий не знает
про Angular, а фронт не знает про Drizzle. Общего у них ровно две вещи:

- **контракт** `docs/api/swagger.json` - источник правды здесь, у фронта копия;
- **словарь домена** `CONTEXT.md` - источник правды у фронта, здесь копии нет.

Второго словаря не заводим: две копии разойдутся, и никто их не синхронизирует.
Нужен термин - читаешь `../messenger/CONTEXT.md`. Новый термин согласуется и
дописывается там же, в репозитории фронта.

Фронт и бэкенд разрабатываются параллельно в двух окнах. Правку, которая
требует синхронного изменения обоих репозиториев, не начинаешь молча -
называешь ее вслух: она стоит двух PR и координации.

## Контракт

Бэкенд реализует «Chat & OAuth API» один в один: те же пути, методы, коды
ответов и состав полей. Фронту для перехода достаточно подменить `apiBaseUrl`.

- Endpoint, метод и состав полей сверяй по `docs/api/swagger.json`, а не по
  памяти и не по коду фронта.
- Переписка в swagger не описана - протокол в `docs/api/websocket.md`.
- Отклонение от контракта - ломающее изменение. Оно заводится отдельным change,
  записывается в `docs/api/README.md` и правится в двух репозиториях синхронно.
  Молча «сделать удобнее» нельзя: фронт сломается.

## Workflow: OpenSpec

Разработка ведется по OpenSpec (`@fission-ai/openspec`, схема `spec-driven`):
сначала меняется спецификация, потом код.

- Источник правды по требованиям - каталог `openspec/`:
  - `openspec/specs/<capability>/spec.md` - согласованное поведение системы;
  - `openspec/changes/<id>/` - предложенное, еще не примененное изменение;
  - `openspec/config.yaml` - контекст проекта и язык артефактов.
- Change содержит `proposal.md` (что и зачем), дельту спеков в
  `changes/<id>/specs/<capability>/spec.md`, `design.md` (как) и `tasks.md`
  (шаги реализации).
- Планирование и реализация разделены: после создания артефактов остановись и
  дождись явного запроса на реализацию.
- `npx openspec validate --strict` на любом заведенном change обязан быть
  зеленым. Красная валидация всегда означает поломку.
- Реализация идет блоками: блок - это одна секция `tasks.md` (`## N. ...`).
  Закончив блок, остановись и дождись апрува.
- В конце блока покажи: какие задачи закрыты, какие файлы созданы и изменены,
  результат `npm run lint`, `npm run test:ci` и `npm run test:e2e`.
- Требование формулируется как поведение с проверяемыми сценариями
  (`### Requirement:` + `#### Scenario:`), а не как описание реализации.
- Артефакты пишем на русском; структурные заголовки OpenSpec и ключевые слова
  `SHALL`/`MUST` остаются на английском.
- Без change обходятся только правки, не меняющие поведение: рефакторинг,
  конфигурация, документация, исправление сборки.

## Workflow: GitHub

Issue отвечает на «зачем и когда», change - на «что и как». Требования живут
только в change, issue их не дублирует.

- Тело issue - цель, milestone и ссылка на `openspec/changes/<id>/`.
- Ветку заводи из issue: `gh issue develop <N> --base main --checkout`.
- `Closes #N` ставится в теле финального PR из ветки issue в `main`.
- В `proposal.md` change указывай `Issue: #N`.

### Формат коммитов

[Conventional Commits](https://www.conventionalcommits.org/):
`<type>(<scope>): <description>`. Проверяет commitlint в хуке `commit-msg`.

- Типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`, `build`, `ci`,
  `perf`, `style`, `revert`.
- Скоуп необязателен, но если указан - только из `scope-enum` в
  `commitlint.config.js`. Скоупы доменов совпадают со скоупами фронта: домен у
  репозиториев общий.
- Описание - на английском, в нижнем регистре, повелительным наклонением, без
  точки в конце: `feat(identity-access): add signup endpoint`.
- Заголовок PR - тоже по Conventional Commits: репозиторий мержит squash.

### Ревью блоков

Блок ревьюется как отдельный PR в ветку issue. Ветка issue - интеграционная.

- Ветка блока - от актуальной ветки issue, имя `<issue>-<секция>-<слаг>`.
- Закончив блок: коммит, push ветки блока, PR `ветка блока -> ветка issue`.
- Историю ветки блока не переписываешь: rebase и force-push отвязывают
  комментарии ревью от строк. Только новые коммиты сверху.
- PR блока мержишь ты, squash.
- Когда все блоки смержены - PR `ветка issue -> main` с `Closes #N` в теле.
