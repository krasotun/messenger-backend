## Context

Мотивация - в `proposal.md`, требования - в `specs/identity-access/spec.md`.
Здесь только то, как это устроено.

Состояние на входе: схема БД пуста, есть пустая миграция `InitialCreate`,
`MessengerDbContext` без сущностей. В `Program.cs` уже настроены snake_case для
JSON, тело ошибки `{ reason }` вместо `ProblemDetails` и `UseStatusCodePages`,
который для `401` намеренно оставляет тело пустым - ровно то, чего требует
спека.

Механизм сессии контракт не описывает: `securityDefinitions` в
`docs/api/swagger.json` пуст. Форма сессии восстановлена по фронту -
`../messenger/docs/adr/2026-05-12-session-lives-in-backend-cookie.md`: сессией
владеет бэкенд, носит ее `HttpOnly` cookie, фронт шлет все запросы с
`withCredentials: true` и имя cookie не знает.

## Goals / Non-Goals

**Goals:**

- Механизм сессии, на который встанут все последующие эндпоинты: контроллеру
  достаточно потребовать аутентификацию и получить **Текущего пользователя**.
- Первые таблицы схемы в форме, пригодной для профиля и чатов, - они придут
  следующими change и будут ссылаться на пользователя.

**Non-Goals:**

- Отзыв всех сессий пользователя, ограничение их числа, список активных
  устройств. Контракт таких эндпоинтов не описывает.
- Ограничение частоты попыток входа и блокировка учетной записи.
- Обновление профиля, смена пароля и аватара - отдельные эндпоинты и отдельные
  change.

## Decisions

### Сессия - строка в таблице, cookie несет только идентификатор

Cookie несет непрозрачный случайный идентификатор, а состояние сессии живет в
таблице `sessions`.

Альтернативы: шифрованный тикет ASP.NET Core cookie authentication без
хранилища и JWT в cookie. Обе отклонены по одной причине: спека требует, чтобы
завершенная сессия переставала признаваться немедленно, а самодостаточный
токен остается валидным до истечения - выход был бы косметикой. Плюс тикет
шифруется ключами Data Protection, которые пришлось бы отдельно переживать
рестарт контейнера; таблица эту заботу снимает.

Цена решения - запрос к БД на каждый аутентифицированный вызов. Она невелика:
эти вызовы и так идут в БД за данными.

### В таблице хранится хеш идентификатора сессии, не он сам

Идентификатор - 32 случайных байта от `RandomNumberGenerator`, клиенту он
уходит в base64url. В таблице лежит его SHA-256.

Утечка содержимого таблицы - через бэкап, лог или SQL-инъекцию - тогда не дает
угнать сессии: по хешу восстановить cookie нельзя. Для случайного
128+-битного секрета хеширования без соли достаточно, перебор здесь не
применим. Стоимость - один SHA-256 на запрос.

### Пароль хеширует `PasswordHasher<T>` из состава ASP.NET Core

`Microsoft.Extensions.Identity.Core` входит в shared framework
`Microsoft.AspNetCore.App` (проверено в `10.0.11`), поэтому
`PasswordHasher<User>` доступен без нового NuGet-пакета и без остальной
Identity - ни `IdentityDbContext`, ни `UserManager`, ни ее таблиц.

Он дает PBKDF2-SHA256, соль внутри значения и формат с маркером версии, то
есть будущую смену параметров без миграции данных: `VerifyHashedPassword`
возвращает `SuccessRehashNeeded`, и пароль можно перехешировать при следующем
успешном **Входе**.

Альтернативы - BCrypt.Net или Argon2 сторонним пакетом. Отклонены: сильнее по
параметрам, но добавляют зависимость там, где платформа закрывает задачу сама.

### Аутентификацию делает схема authentication, а не проверка в контроллере

Заводится своя `AuthenticationHandler`, читающая cookie и поднимающая
**Текущего пользователя**. Контроллеры помечаются `[Authorize]`.

Так `401` для `GET /auth/user` выдает платформа, и он приходит с пустым телом -
`UseStatusCodePages` в `Program.cs` для `401` уже сделан молчащим. Ручная
проверка в каждом действии дала бы тот же результат ценой повторения в каждом
будущем контроллере, а их впереди почти весь контракт.

### Атрибуты cookie

`HttpOnly` и `Path=/` - требование спеки. `SameSite=Lax` и `Secure` из
конфигурации, по умолчанию выключенный `Secure` для локального `http`.

Cross-site сценарий - фронт на другом origin - в этом change не решается: он
требует CORS с credentials, который вынесен отдельным change. Там же
`SameSite` при необходимости станет `None`, и `Secure` станет обязательным:
браузер `SameSite=None` без `Secure` не примет.

### Срок жизни сессии - 14 суток, абсолютный

Отсчитывается от **Входа** и не продлевается активностью. Значение в
конфигурации.

Скользящее окно потребовало бы записи в БД на каждый запрос ради удобства,
которого никто не просил; контракт про срок жизни молчит вовсе. Истекшая
сессия для клиента неотличима от завершенной - оба случая дают `401`, как
требует спека.

### Уникальность логина и email проверяется базой, а не предварительным чтением

Уникальные индексы на `login` и `email`; при регистрации ловится нарушение
уникальности от Postgres и превращается в `400`.

Предварительный `SELECT` не спасает от гонки: два одновременных запроса с
одинаковым логином оба его пройдут. Индекс - единственная проверка, которая не
врет. Сравнение точное, без нормализации регистра: контракт объявляет поля
уникальными, но про регистр не говорит ничего, а нормализация была бы
поведением, которого он не просил.

### Пустое тело для ответов без схемы

`200` без `schema` в контракте - ответ без тела (`CLAUDE.md`, раздел
«Контракт»). В ASP.NET Core это `Ok()` без значения, а не `NoContent()`:
последний дал бы `204`, то есть другой код, чем в контракте.

## Risks / Trade-offs

- **Тесты этого change первыми идут в живую БД, а инфраструктура для этого
  вынесена в отдельный change** → e2e гоняются по поднятому `docker compose`, с
  миграциями, накатанными руками, и с уникальными логинами на тест, чтобы
  прогоны не мешали друг другу. Как только инфраструктурный change закроется,
  эти тесты переедут на него без правки проверок.
- **Фронтом эту авторизацию проверить нельзя до change про CORS** → проверка
  только тестами и вручную через HTTP-клиент. Риск в том, что расхождение с
  ожиданиями фронта всплывет позже; снижаем тем, что форма ответов сверена по
  контракту и по коду фронта заранее.
- **Запрос к БД за сессией на каждый аутентифицированный вызов** → индекс по
  хешу идентификатора; при росте нагрузки перед оптимизацией нужны измерения, а
  не догадки.
- **Истекшие сессии копятся в таблице** → на корректность не влияют, проверка
  срока идет по `expires_at`. Уборка - позже, когда будет что убирать.

## Migration Plan

Одна миграция EF Core: таблицы `users` и `sessions`. Разворачивание - накат
миграции перед стартом новой версии; откат - `Down` этой же миграции, данных на
момент выката нет, поэтому потерять нечего.

## Open Questions

- Нужен ли `SuccessRehashNeeded`-перехеш пароля при входе уже в этом change или

  задач не влияет.
- Чем убирать истекшие сессии - фоновым сервисом или командой обслуживания.
  Решается, когда появится эксплуатация.
