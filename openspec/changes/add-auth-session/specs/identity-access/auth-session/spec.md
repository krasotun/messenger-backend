## Purpose

Регистрация пользователя, вход по логину и паролю, выяснение текущего
пользователя по серверной сессии и выход. Здесь же живут правила хранения
пароля, жизни session cookie и доступа остальных эндпоинтов API к текущему
пользователю.

## ADDED Requirements

### Requirement: Регистрация пользователя

Система SHALL создавать пользователя по `POST /auth/signup` с телом из полей
`first_name`, `second_name`, `login`, `email`, `password`, `phone` и отвечать
`200` с телом `{ "id": <number> }`.

Вместе с ответом система SHALL устанавливать session cookie: зарегистрировавшийся
человек становится текущим пользователем сразу, без отдельного входа.

`display_name` и `avatar` у нового пользователя SHALL быть пустыми.

#### Scenario: Успешная регистрация

- **WHEN** гость шлет `POST /auth/signup` с корректным телом и свободным логином
- **THEN** ответ `200` с телом `{ "id": <идентификатор нового пользователя> }`
- **AND** ответ несет заголовок установки session cookie
- **AND** последующий `GET /auth/user` с этой cookie возвращает `200` и профиль
  созданного пользователя

#### Scenario: Логин занят

- **WHEN** гость шлет `POST /auth/signup` с логином существующего пользователя
- **THEN** ответ `400` с телом `{ "reason": "Login already exists" }`
- **AND** второй пользователь не создается
- **AND** session cookie не устанавливается

#### Scenario: Email занят

- **WHEN** гость шлет `POST /auth/signup` с email существующего пользователя
- **THEN** ответ `400` с телом `{ "reason": "Email already exists" }`
- **AND** второй пользователь не создается

### Requirement: Валидация тела регистрации

Система SHALL отклонять регистрацию с телом, не удовлетворяющим контракту, кодом
`400` и телом `{ "reason": <текст> }`, и SHALL не создавать пользователя.

Обязательны все шесть полей. `email` SHALL соответствовать `/^\S+@\S+$/`, `phone`

- `/^((8|\+7)[\- ]?)?(\(?\d{3}\)?[\- ]?)?[\d\- ]{7,10}$/`. Пустые строки в
  обязательных полях недопустимы.

#### Scenario: Отсутствует обязательное поле

- **WHEN** гость шлет `POST /auth/signup` без поля `login`
- **THEN** ответ `400` с телом `{ "reason": <текст> }`
- **AND** пользователь не создается

#### Scenario: Email не проходит по формату

- **WHEN** гость шлет `POST /auth/signup` с `email` без символа `@`
- **THEN** ответ `400` с телом `{ "reason": <текст> }`
- **AND** пользователь не создается

#### Scenario: Телефон не проходит по формату

- **WHEN** гость шлет `POST /auth/signup` с `phone` из букв
- **THEN** ответ `400` с телом `{ "reason": <текст> }`
- **AND** пользователь не создается

#### Scenario: Лишние поля в теле

- **WHEN** гость шлет `POST /auth/signup` с корректным телом и лишним полем
  `role`
- **THEN** ответ `400` с телом `{ "reason": <текст> }`

### Requirement: Вход по логину и паролю

Система SHALL принимать `POST /auth/signin` с телом `{ login, password }`,
проверять пароль и при совпадении отвечать `200`, устанавливая session cookie.

Тело успешного ответа SHALL быть текстом `OK`: фронт читает `/auth/signin` как
`text` и состояние сессии из тела не берет.

Ответ на неверные учетные данные SHALL не различать «нет такого логина» и
«неверный пароль»: иначе endpoint становится проверкой существования логина.

#### Scenario: Успешный вход

- **WHEN** гость шлет `POST /auth/signin` с логином и паролем существующего
  пользователя
- **THEN** ответ `200` с телом `OK`
- **AND** ответ несет заголовок установки session cookie
- **AND** последующий `GET /auth/user` с этой cookie возвращает `200` и профиль
  этого пользователя

#### Scenario: Неверный пароль

- **WHEN** гость шлет `POST /auth/signin` с существующим логином и чужим паролем
- **THEN** ответ `400` с телом `{ "reason": "Login or password is incorrect" }`
- **AND** session cookie не устанавливается

#### Scenario: Несуществующий логин

- **WHEN** гость шлет `POST /auth/signin` с логином, которого нет
- **THEN** ответ `400` с телом `{ "reason": "Login or password is incorrect" }`

#### Scenario: Повторный вход при живой сессии

- **WHEN** текущий пользователь шлет `POST /auth/signin` с корректными данными
  другого пользователя
- **THEN** ответ `200`
- **AND** cookie указывает на новую сессию второго пользователя
- **AND** прежняя сессия завершена

### Requirement: Чтение текущего пользователя

Система SHALL отвечать на `GET /auth/user` профилем текущего пользователя в
составе полей контракта: `id`, `first_name`, `second_name`, `display_name`,
`login`, `email`, `phone`, `avatar`. `display_name` и `avatar` SHALL быть `null`,
когда не заданы.

Хеш пароля и любые служебные поля сессии SHALL никогда не попадать в ответ.

Гостю система SHALL отвечать `401`. Это штатный ответ, а не ошибка: фронт
трактует его как отсутствие сессии.

#### Scenario: Сессия есть

- **WHEN** текущий пользователь шлет `GET /auth/user`
- **THEN** ответ `200` с ровно восемью полями контракта
- **AND** в теле нет поля с паролем или его хешем

#### Scenario: Cookie нет

- **WHEN** гость шлет `GET /auth/user` без cookie
- **THEN** ответ `401`

#### Scenario: Cookie указывает на несуществующую сессию

- **WHEN** гость шлет `GET /auth/user` с cookie, чья сессия завершена или
  никогда не существовала
- **THEN** ответ `401`

#### Scenario: Cookie указывает на истекшую сессию

- **WHEN** гость шлет `GET /auth/user` с cookie сессии, у которой истек срок
  жизни
- **THEN** ответ `401`

### Requirement: Выход

Система SHALL по `POST /auth/logout` завершать текущую сессию так, чтобы прежняя
cookie больше никого не опознавала, и сбрасывать cookie у клиента.

Ответ SHALL быть `200` с пустым телом: фронт читает `/auth/logout` как JSON, и
непустое нераспознаваемое тело он считает ошибкой.

Гостю система SHALL тоже отвечать `200`: выход идемпотентен, и контракт для этого
пути `401` не описывает.

#### Scenario: Выход текущего пользователя

- **WHEN** текущий пользователь шлет `POST /auth/logout`
- **THEN** ответ `200` с пустым телом
- **AND** ответ несет заголовок сброса session cookie
- **AND** последующий `GET /auth/user` с прежней cookie возвращает `401`

#### Scenario: Выход без сессии

- **WHEN** гость шлет `POST /auth/logout` без cookie
- **THEN** ответ `200` с пустым телом

#### Scenario: Выход не трогает чужие сессии

- **WHEN** у пользователя две сессии из разных браузеров и он выходит в одной
- **THEN** вторая сессия продолжает опознавать его на `GET /auth/user`

### Requirement: Session cookie

Система SHALL опознавать текущего пользователя только по session cookie: другие
способы передать сессию не поддерживаются.

Значение cookie SHALL быть криптографически случайным идентификатором, по
которому нельзя вычислить ни идентификатор пользователя, ни значение другой
сессии.

Cookie SHALL выставляться с `HttpOnly` и `Path=/`, а признак `Secure` и режим
`SameSite` SHALL браться из конфигурации окружения: локальный стенд ходит по
`http` с другого порта, публичный - по `https` с другого домена.

Сессия SHALL иметь конечный срок жизни, задаваемый конфигурацией.

#### Scenario: Cookie недоступна скриптам

- **WHEN** система устанавливает session cookie
- **THEN** заголовок несет `HttpOnly` и `Path=/`

#### Scenario: Значения сессий не предсказуемы

- **WHEN** два входа подряд создают две сессии
- **THEN** значения cookie различаются и не выводятся одно из другого

#### Scenario: Сессия в теле или заголовке не принимается

- **WHEN** гость шлет `GET /auth/user` с идентификатором сессии в заголовке
  `Authorization` вместо cookie
- **THEN** ответ `401`

### Requirement: Хранение пароля

Система SHALL хранить пароль только в виде хеша с индивидуальной солью и
параметрами стойкости, пригодными для паролей. Исходный пароль SHALL не
сохраняться и не логироваться.

Сравнение пароля при входе SHALL быть устойчивым к атаке по времени.

#### Scenario: В хранилище нет исходного пароля

- **WHEN** пользователь зарегистрировался
- **THEN** в записи пользователя нет поля с исходным паролем
- **AND** сохраненное значение не совпадает с введенным паролем

#### Scenario: Одинаковые пароли дают разные хеши

- **WHEN** два пользователя зарегистрировались с одним и тем же паролем
- **THEN** сохраненные значения различаются

### Requirement: Доступ к API от имени текущего пользователя

Система SHALL предоставлять единый механизм, который для защищенного эндпоинта
проверяет сессию и дает обработчику текущего пользователя, а гостю отвечает
`401` до входа в обработчик.

Пути `POST /auth/signup`, `POST /auth/signin`, `POST /auth/logout` и
`GET /api/v2/health` SHALL быть доступны гостю.

#### Scenario: Защищенный эндпоинт без сессии

- **WHEN** гость обращается к эндпоинту, требующему сессии
- **THEN** ответ `401`
- **AND** обработчик эндпоинта не выполняется

#### Scenario: Публичный эндпоинт доступен гостю

- **WHEN** гость шлет `GET /api/v2/health`
- **THEN** ответ `200`

### Requirement: Формат ошибки

Система SHALL отвечать на ошибку `4xx` и `5xx` телом `{ "reason": <текст> }` из
контракта, кроме `401`, для которого контракт тела не описывает.

Текст `reason` SHALL не раскрывать внутренности: ни SQL, ни стек, ни имена
таблиц.

#### Scenario: Ошибка клиента

- **WHEN** запрос отклонен с кодом `400`
- **THEN** тело ответа - JSON с единственным полем `reason`

#### Scenario: Внутренняя ошибка

- **WHEN** обработка запроса падает с необработанной ошибкой
- **THEN** ответ `500` с телом `{ "reason": <текст без деталей реализации> }`

### Requirement: Кросс-доменные запросы с сессией

Система SHALL принимать запросы с cookie от origin фронта: фронт живет на другом
адресе и шлет все запросы с `withCredentials: true`.

Список разрешенных origin SHALL задаваться конфигурацией окружения, а не быть
зашитым в код и не быть произвольным: с `credentials` разрешать любой origin
нельзя.

#### Scenario: Запрос с разрешенного origin

- **WHEN** браузер шлет запрос с origin из списка разрешенных
- **THEN** ответ несет `Access-Control-Allow-Origin` с этим origin и
  `Access-Control-Allow-Credentials: true`

#### Scenario: Запрос с постороннего origin

- **WHEN** браузер шлет запрос с origin вне списка
- **THEN** ответ не несет заголовков разрешения кросс-доменного доступа
